Порядок загрузки mise.toml при активации окружения

Ресерч делался на основе версии 2025.11.3

Когда у вас настроена интеграция mise с shell (eval "$(mise activate bash)") и вы переходите в директорию с mise.toml, mise автоматически загружает конфигурацию и настраивает окружение. Важно понимать в каком порядке это происходит, чтобы правильно выстраивать зависимости между секциями.

Порядок загрузки

┌─────────────────────────────────────────────────────────────────────────┐
│              Порядок загрузки при cd в папку                            │
├─────────────────────────────────────────────────────────────────────────┤
│ 1. [vars]            - переменные для шаблонов                          │
│ 2. [alias]/[plugins] - опционально                                      │
│ 3. [env] БЕЗ tools   - базовые переменные окружения (первый проход)     │
│ 4. [tools]           - установка/проверка инструментов                  │
│ 5. [env] С tools     - переменные после установки tools (второй проход) │
│ 6. Применение        - export в shell                                   │
└─────────────────────────────────────────────────────────────────────────┘

Ключевые правила

  • [[env]] блоки выполняются в порядке написания в файле, по этому, если важен порядок, используйте их вместо одного блока [env]
    • но с учетом двух проходов: сначала директивы БЕЗ tools=true, потом С tools=true
    • несколько директив с tools=true будут загружаться в порядке объявления
  • vars НЕ может использовать env или tools
  • env может использовать vars ВСЕГДА
  • env может использовать tools ТОЛЬКО когда директива имеет параметр tools=true
  • _.python.venv ВСЕГДА имеет tools=true (нельзя изменить)
  • Порядок _.* директив внутри [env] жестко закодирован: _.path → _.file → _.source → другие → _.python.venv

Доступность данных в templates

Секция vars env (pass 1) tools env (pass 2)
[vars] ✅ ❌ ❌ ❌
[env] pass 1 ✅ ✅ ❌ ❌
[env] pass 2 ✅ ✅ ✅ ✅

Что доступно в шаблонах:

  • {{config_root}} - путь к директории с mise.toml
  • {{cwd}} - текущая рабочая директория
  • {{vars.NAME}} - переменные из [vars]
  • {{env.NAME}} - переменные окружения

Примеры решения проблем

Использование VIRTUAL_ENV без установки tools=true

[[env]]
_.python.venv = { path = ".venv", create = true }
MY_PATH = "{{env.VIRTUAL_ENV}}/data"  # ❌ VIRTUAL_ENV еще нет!

Решение: добавьте tools = true

[[env]]
MY_PATH = { value = "{{env.VIRTUAL_ENV}}/data", tools = true }  # ✅

Переменная VIRTUAL_ENV создается после того как инициализированы tools и после _.python.venv, а обычные переменные окружения без tools = true загружаются на первом проходе.

Использование env в vars

[vars]
OTHER_VAR = "{{env.MY_VAR}}"  # ❌ env не доступны в vars!

Решение: используйте vars или переместите в [env]

[vars]
OTHER_VAR = "{{vars.MY_VAR}}"  # ✅

Скрипт выполняется до установки tools

[[env]]
_.source = "setup.sh"  # ❌ Скрипту нужен Python, но его еще нет!

Решение: добавьте tools = true

[[env]]
_.source = { path = "setup.sh", tools = true }  # ✅

Ожидание порядка _.* директив внутри [env]

Порядок выполнения директив жестко закодирован: _.file → _.source → _.python.venv

[env]
_.python.venv = { path = ".venv", create = true }
_.source = "script.sh"
_.file = ".env"

Решение: объявите отдельные [[env]] блоки и расположите их в нужном порядке (но не забывайте, что параметр tools оказывает все равно влияение на порядок загрузки и что есть 2 прохода)

[[env]]
_.file = ".env"

[[env]]
_.source = "script.sh"

[[env]]
_.python.venv = { path = ".venv", create = true }

Как хранить секреты в проектах: sops and age

Секреты проекта лежат рядом с кодом в зашифрованном файле, а mise расшифровывает их и подставляет в переменные окружения при входе в директорию.

Зачем. Главная цель - закрыть секреты от AI-агентов, работающих с проектом. В файле лежит только шифротекст, а приватный ключ хранится вне проекта, в ~/.config/sops/age/. Вторая половина защиты - изоляция: агенты запускаются в agentbox, отдельном контейнере, куда примонтирован только текущий проект. Ключа там нет, поэтому расшифровать файл агент не сможет, даже если попытается.

Чего способ не даёт. Это не «безопасное хранилище» и не защита от того, у кого есть доступ к машине:

  • приватный ключ лежит на диске открытым текстом, вся защита - права на файл;
  • любой процесс, запущенный на хосте от твоего пользователя, прочитает и ключ, и расшифрованные значения;
  • после подстановки значения живут в переменных окружения открытым текстом;
  • ротация и отзыв ключей делаются руками.

1. Установка

brew install sops age

age нужен только для генерации ключа, sops - для шифрования и редактирования. Расшифровывает mise сам, встроенным rops.

2. Генерация ключа

mkdir -p ~/.config/sops/age
age-keygen -o ~/.config/sops/age/keys.txt
chmod 600 ~/.config/sops/age/keys.txt

В файле окажется приватный ключ (AGE-SECRET-KEY-1...) и публичный комментарием (# public key: age1...).

Если секреты не хранятся используемые в проекте больше ни где не дублируются, нужно быть особенно аккуратным с содержимым файла keys.txt и сделать его бепап. Потому что в случае его полной утраты будет не возможно более расшифровать содержимое файлов с секретами.

3. Переменные окружения

В ~/.zshrc:

export SOPS_AGE_KEY_FILE="$HOME/.config/sops/age/keys.txt"
export SOPS_AGE_RECIPIENTS="$(age-keygen -y $HOME/.config/sops/age/keys.txt)"
  • SOPS_AGE_KEY_FILE - чем расшифровывать (приватный ключ)
  • SOPS_AGE_RECIPIENTS - чем шифровать (публичный ключ)

age-keygen -y достаёт публичный ключ из приватного, поэтому хардкодить age1... не нужно - перегенерируешь ключ, всё подхватится. Благодаря этим переменным .sops.yaml в проектах не нужен.

Перезапускаем шелл или source ~/.zshrc и проверяем:

echo $SOPS_AGE_RECIPIENTS   # должна быть строка age1...

4. Создание файла с секретами

Важно: пустой файл не годится. sops парсит содержимое в структуру, а из пустого файла структуры не получается. Симптом: Could not unmarshal input data: EOF

Впервый раз создать файл с секретами можно одним из следующих методов.

Метод 1. Через sops, который создаст файл с дефолтным шаблоном и откроет в редакторе по умолчанию:

sops .env.sops.yaml

Метод 2. Создать файл с будующими секретами самому и потом просто открыть его на редактирование. Надёжнее, не зависит от версии sops (-e - зашифровать, -i - на месте, перезаписав файл):

cat > .env.sops.yaml <<'EOF'
DATABASE_URL: postgresql://localhost/mydb
API_KEY: sk_test_abc123
EOF

sops -e -i .env.sops.yaml

Про YAML. Значения yes, no, on, off, true, false и числа с ведущим нулём YAML приведёт к своим типам, а не к строке. Для секретов всплывает редко, но если попалось - оберни в кавычки:

FEATURE_FLAG: "no"
FILE_MODE: "0755"

Комментарии, в отличие от JSON, поддерживаются - удобно помечать источник секрета или срок ротации:

# ротировать до 2026-12-01
STRIPE_KEY: sk_test_xyz

Проверка, что зашифровалось

head -c 200 .env.sops.yaml

Должно быть ENC[AES256_GCM,...] вместо значений. Имена переменных остаются читаемыми - это нормально и удобно для code review.

5. Подключение к mise

В mise.toml:

[env]
_.file = ".env.sops.yaml"

После этого переотркываем косоль или переактивируем mise, чтобы он переинициализовал окружение и проверяем.

mise env | grep DATABASE_URL

Запуск там, где ключа нет

По умолчанию mise падает, если не может расшифровать файл:

mise ERROR failed to decrypt sops file
mise ERROR unable to retrieve data key
mise ERROR no data key retrieved from metadata

Типичная ситуация - контейнер, CI или чужая машина: mise.toml и .env.sops.yaml приехали вместе с репозиторием, а приватного ключа там нет и быть не должно.

Лечится настройкой sops.strict. При false mise пропускает расшифровку и продолжает с остальным окружением вместо того, чтобы падать.

Вариант А. Переменная окружения

Только в том месте, где ключа нет:

ENV MISE_SOPS_STRICT=0

На хосте поведение остаётся строгим.

Вариант Б. В mise.toml

[settings]
sops.strict = false

[env]
_.file = ".env.sops.yaml"

Проще, но действует везде, включая твою машину. Сломается ключ - приложение молча стартует с пустыми переменными вместо внятной ошибки.

Таски для Zed

Пример тасок для zed, которые позволят редактировать и просматривать секреты.

[
  {
    "label": "sops: edit secrets",
    "command": "sops",
    "args": [".env.sops.yaml"],
    "env": { "EDITOR": "zed --wait" },
    "use_new_terminal": false,
    "allow_concurrent_runs": false,
    "reveal": "no_focus"
  },
  {
    "label": "sops: show secrets",
    "command": "sops",
    "args": ["-d", ".env.sops.yaml"],
    "reveal": "always"
  }
]
